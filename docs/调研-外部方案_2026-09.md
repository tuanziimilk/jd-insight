# 调研：四个外部方案对 JD Insight 对话系统的可用性

> 2026-09-11 · 调研对象：DeerFlow（字节）· ChatGPT Web 记忆系统逆向 · nanobot · pi agent
> 结论先行：**只有一个值得直接抄（pi 的 hook 分层），一个值得抄思路不抄实现（ChatGPT 的记忆分层），
> 两个明确不采纳（DeerFlow / nanobot 都是"整套 harness"，我们不需要 harness）。**

判断标准沿用 ROADMAP v3.0 那条：**先问确定性/手写方案够不够，不够才加那一层。**
以及一条新的：**任何方案要进来，必须能单独进来** —— 要求换掉 `sidepanel.js` 里 `ask()` 那条链路的都不要。

---

## 1. DeerFlow（bytedance/deer-flow）

**它是什么**：LangGraph 上的长任务 SuperAgent harness。supervisor 编排 + subagent、
沙箱（local/docker/k8s）、checkpoint 恢复、持久记忆、渐进式 skill 加载（skill = 一个 md 文件，
用到才进上下文）、报告合成。定位是"跑几分钟到几小时的深研究任务"。

**对我们有没有用**：整体 ❌，两个局部 ✅。

| 它的设计 | 对 JD Insight | 判断 |
|---|---|---|
| LangGraph supervisor + subagent | 我们的路径能事先枚举（6 个意图），ROADMAP 已经写明"能枚举就别上 Agent" | ❌ 不采纳 |
| 沙箱执行 | 我们没有代码执行 | ❌ 无关 |
| checkpoint / 长任务恢复 | 我们单轮 5 秒出结果 | ❌ 无关 |
| **渐进式 skill 加载** | 对应我们的**提示词分块**：现在诊断/改写/面试的指令大概率都拼进同一个 system prompt | ⚠️ 值得借鉴 |
| **report 合成带引用** | 正是 v2.1 第 2 项「引用校验」的下游 | ⚠️ 值得借鉴 |

> ⚠️ **更正（2026-09-11，读代码后）**：这条我原本列成待办，其实**已经做完了**。
> `intents.js` 的 `systemPrompt()` 不但按意图分块（DIAGNOSE / REWRITE / PREP 各自 push 指令块），
> 还有一整段注释在讲前缀缓存顺序：base 硬规则 → 简历 → 意图指令 → 降级标记 → 检索结果，
> 并记录了「之前把意图指令放在简历前面，换个意图就把几千 token 的简历踢出缓存」这个已修的坑。
> **DeerFlow 那条只是佐证，不是待办。**

**不采纳 LangGraph 的理由没变**：它的成本不表现为 bug，表现为失去对提示词拼装顺序的控制，
而那一点直接进账单。

## 2. ChatGPT Web 记忆系统的逆向（最有价值的一篇）

**逆出来的结构**（Shlok Khemani 等几篇一致）：四类，全部**每轮全量注入**，不做检索。

| 类别 | 内容 | 谁写的 |
|---|---|---|
| `user interaction metadata` | 设备、对话深度、各话题消息量、模型使用占比、地理位置估计 | 系统自动 |
| `recent conversation content` | 最近约 40 条会话的**用户消息**（不含回复）+ 时间戳，作"连续性日志" | 系统自动 |
| `model set context` | 用户明说"记住…"产生的短句，带时间戳，**冲突时优先级最高** | 用户显式 |
| `user knowledge memories` | 模型定期从历史里蒸出的 ~10 段稠密画像 | 模型生成 |

**关键发现是检索策略：不检索，全量塞。** 作者称之为"苦涩的教训"式赌注 ——
赌模型变强、上下文变长、成本下降，于是不值得为记忆做复杂检索。
批评也在这里：**旧上下文会污染新问题，而用户没有办法让它别管。**

**对我们的用处（这是四个里最直接的）**：ROADMAP v3.0「长期记忆」那一格现在是空的，
前置条件写着"有采纳/拒绝的反馈按钮"（= P2 的 HITL）。这篇逆向直接给了**分层的字段设计**，
而且给了一个我们应该**反着做**的点：

**建议的记忆分层（照抄分类，不照抄注入策略）**

| 我们的层 | 对应 | 存什么 | 注入策略 |
|---|---|---|---|
| **事实层**（用户显式） | `model set context` | "我是 3 年半 AI PM"、"目标岗位是出海产品"、"报价下限 X" | ✅ 全量注入，冲突时最高优先级 |
| **画像层**（模型蒸馏） | `user knowledge memories` | 从简历 + 历次诊断蒸出的能力画像 | ✅ 全量注入，但**必须可编辑** |
| **偏好层**（HITL 反馈） | 无对应 | "哪类改写建议被采纳/拒绝了" | ⚠️ 只在 `REWRITE`/`DIAGNOSE` 意图注入 |
| **会话日志层** | `recent conversation content` | 最近问过什么 | ❌ **不做** |

反着做的两处，理由都很具体：

1. **不做"全量注入"**，按意图注入。ChatGPT 敢全量是因为它不知道用户下一句要干嘛；
   我们**有意图识别**，`STATS`/`GAP` 是确定性计算根本不进模型，给它塞画像是纯浪费。
   我们已经付了意图识别这笔成本，就该吃它的红利。
2. **不做会话日志层**。求职场景里"我上周问过什么"几乎不影响"这条 JD 要什么"，
   而它是最大的一块 token，也是最容易造成污染的一块。

3. **画像层必须可编辑，而且要标"这是模型猜的"**。这和 P0 那条经验是同一条：
   `analyzer/config.py` 的示例占位被当成真实能力印进报告过。
   **模型蒸出来的画像如果不可见不可改，就是同一个坑的第二次。**
   落点现成：career-web 的 **07 校准台**已经有"能力自评编辑"，画像层挂在那里。

**另一篇的反向意见值得一起记**（"Most AI Products Shouldn't Ship Memory"）：
记忆的失败模式是**沉默的** —— 它不报错，只是让答案慢慢跑偏，而用户不知道为什么。
所以记忆上线的前提应该和引用校验一样：**能被看见、能被关掉**。

## 3. nanobot

注意有**两个同名项目**：

- `nanobot-ai/nanobot`（Go）：MCP host，做 MCP + MCP-UI 聊天机器人。**已停止接受外部 PR 和新功能**。
- `HKUDS/nanobot`（Python）：轻量自托管个人 agent —— 推理、工具执行、记忆、定时、多平台聊天接入、MCP。

**判断：❌ 不采纳，但它验证了一个我们已有的判断。**

我们是**浏览器扩展**，MV3 零构建、CSP 禁远程脚本（这是 v2.15 拒绝 supabase-js 的同一个约束）。
一个 Python 自托管 agent 要求用户开一个常驻进程 —— 这比 v2.15 那个"自带 Supabase"的门槛还高，
而换回来的只是我们不需要的多平台接入和定时。

**唯一值得看的**：如果将来真到 v3.0 需要统一工具接入，ROADMAP 已经写了"先看 MCP 不是 LangChain"。
nanobot 是 MCP host 的一个轻量参考实现，**到那时再看，现在不动**。

## 4. pi agent（pi.dev）—— 唯一建议直接抄的

**它是什么**：终端编码 agent，真正的设计点在**扩展的生命周期 hook**：

- 每轮发给 LLM **之前**注入消息
- **过滤/改写消息历史**
- **压缩（compaction）之前**介入 —— 可以做话题压缩、用另一个更便宜的模型压
- 工具被调用时、会话开始时

生态里已经长出 `pi-memory`（长期记忆 + scratchpad + 每日日志）、`agentmemory`
（跨 Claude Code / Codex / Gemini CLI 共享记忆）这类扩展。

**为什么这个对我们最有用**：它不是给我们一个 agent，是给了一个**结构**——
"记忆/检索/注入都不是主流程的一部分，是挂在主流程上的钩子"。

我们现在的对话主链路是 `sidepanel.js` 里的 `ask()`（`pipeline.js` 是投递漏斗的数据模型，不是这条链），一条直链：意图 → 槽位 → 检索 → 拼 prompt → 调模型。
记忆一旦要加，最自然的写法是往这条链里插一段，然后它就和检索、槽位缠在一起 ——
以后想回答"这次回答为什么偏了"就没法单独摘出记忆这一层。

**建议的落地（小、且能马上做）**：把 `ask()` 抽成 `lib/turn.js`，开两个口子，不改任何现有逻辑：

| hook | 时机 | 第一个用途 | 后续用途 |
|---|---|---|---|
| `beforeCompose(ctx)` | 检索完、拼 prompt 前 | 注入记忆层（按意图过滤） | 注入用户偏好 |
| `afterAnswer(ctx, answer)` | 模型返回后 | **引用校验**（v2.1 第 2 项）、幻觉自检（第 3 项） | HITL 采纳/拒绝按钮写回偏好层 |

关键在于 `afterAnswer` **正好是 v2.1 第 2/3 项的挂载点**，而那两项是 P1 的内容 ——
也就是说这个重构不是"为了将来的记忆"，**它的第一个用户就是下一步要做的事**。
这满足"必须能单独进来"。

## 结论与建议顺序

| 优先级 | 动作 | 来源 | 成本 |
|---|---|---|---|
| **P1 内，先做** | 把 `ask()` 抽成 `lib/turn.js`，开 `beforeCompose` / `afterAnswer` 两个 hook，第一个消费者是引用校验 | pi | 小 |
| ~~P1 内~~ **已完成** | 按意图装载提示词块 —— 查代码后更正：`intents.js` 的 `systemPrompt()` 早就这么做了，且前缀缓存顺序有专门注释 | DeerFlow skill 加载 | —— |
| **P2 一起做** | 记忆三层（事实 / 画像 / 偏好），**按意图注入**、画像层挂 07 校准台可编辑可标来源 | ChatGPT 逆向（反着用） | 中 |
| 不做 | LangGraph / supervisor / 沙箱 / 多 agent | DeerFlow | —— |
| 不做 | 自托管 Python agent、多平台接入 | nanobot | —— |
| 不做 | 会话日志层记忆（最近 N 轮全量注入） | ChatGPT 的 `recent conversation content` | —— |

> 这轮调研最该记住的一句：**ChatGPT 敢不做检索，是因为它不知道你下一句要干什么。
> 我们做了意图识别，就不该再交那笔"全量注入"的学费。**
