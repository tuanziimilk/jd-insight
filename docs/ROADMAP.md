# 升级路线

按「投入 × 对用户的价值」排的。**每一项都写了「什么时候才值得做」——没到条件就不做，
这是刻意的：过早优化比缺功能更贵。**

---

## v2.1 · 让结论能被验证（最该先做）

> 这一版不加新功能，加**可信度**。市面上同类工具全都在做「提取 + 打分 + 改写」，
> 几乎没有一个回答「这个结论准不准」——这里是唯一的差异化空间。

| # | 做什么 | 为什么现在做 |
|---|---|---|
| 1 | **标杆集跑测脚本** —— `eval/` 里的问题批量跑，输出得分表 | 现在改提示词全靠感觉，没有回归保护 |
| 2 | **引用校验** —— 检查回答里的【JD n】是否真的对应检索到的那条 | 引用错位是最隐蔽的幻觉，用户不会发现 |
| 3 | **幻觉自检** —— 把回答里的事实性断言回检 JD 原文，标出无出处的句子 | 求职决策不该建立在编的信息上 |
| 4 | **版本对比** —— 两版提示词跑同一批问题，**逐条 diff 并高亮变坏的** | 只看总分会漏掉「涨了整体、坏了某类」 |

**完成标志**：改任何提示词后能一条命令跑完回归，并看到「哪几条变坏了」。

## v2.2 · 采集体验

| # | 做什么 | 什么时候才值得做 |
|---|---|---|
| 1 | 列表页批量勾选（仍需人工点，不自动翻页） | 单条采集用了 50+ 次、确认流程稳定后 |
| 2 | 薪资批量补录界面（弹窗里一次补多条，替代逐条 prompt） | 跳过率 > 30% 时 |
| 3 | 采集时自动打标（意向度 / 已投 / 已挂） | 开始真实投递、需要追踪状态时 |
| 4 | 更多站点适配 | **已确认要做**，见下方专节 |

### 多站点适配（已确认要做，按难度分三层）

现在只有 BOSS 直聘适配完整。**先把 BOSS 用到稳，再一层层往外扩**——
每加一个站点都要重新处理它的 DOM 结构、反爬手段和协议边界，一次铺开必然全都半成品。

| 层 | 站点 | 难度 | 要处理什么 |
|---|---|---|---|
| **L0 已完成** | BOSS 直聘 | —— | SPA 内嵌详情面板 · jobId 做去重键 · 字体反爬（薪资交人工补） |
| **L1 next** | 猎聘 · 智联招聘 | 中 | 结构相对传统，多为独立详情页；启发式兜底大概率已经能抓到正文，主要是补选择器和确认字段位置 |
| **L2** | 前程无忧 · 拉勾 | 中 | 拉勾的岗位量已明显萎缩，性价比低；51job 结构较老但页面较杂 |
| **L3 单独对待** | LinkedIn | **不做扩展适配** | 见下 |

**为什么 LinkedIn 要单独判断：**

海外站已经有成熟方案 —— [JobSpy](https://github.com/speedyapply/JobSpy)（`pip install python-jobspy`）
一个库同时覆盖 LinkedIn / Indeed / Glassdoor / Google / ZipRecruiter，输出 DataFrame。

所以 LinkedIn 的正确做法不是给扩展再写一套选择器，而是**在 `analyzer/` 侧加一个可选的
JobSpy 导入脚本**，把结果转成同样的 `#元信息 + 正文` 块格式喂给 `analyze_jd.py`。

> 判断依据：**同一个问题已经有成熟方案时，接进来比重写划算。**
> 扩展的价值在于"抓登录墙后面、只有人眼能看到的页面"；公开可抓的站点没必要走扩展。

**加一个国内站点具体要做什么**（欢迎 PR）：

1. `extension/manifest.json` 的 `matches` 和 `host_permissions` 里加域名
2. `extension/content.js` 的 `scope()` 里加该站的详情容器选择器
3. `pick()` 的各字段选择器列表里补几条
4. `extension/popup.js` 的 `SITE_NAME` 里加站点名映射

**兜底策略保证即使 2~3 步都不做也能用**：启发式会扫出正文，整页文本永远兜底。
所以「支持一个新站点」的最低成本其实只有第 1 步。

## v3.0 · 从「问答」到「Agent」

**现在的对话是单轮工具调用（检索 → 生成），不是 Agent。**
要成为 Agent，得让「下一步做什么」由模型临场决定：

| 能力 | 举例 | 前置条件 |
|---|---|---|
| 多步规划 | 「帮我准备这家公司的面试」→ 自己决定：先查这家 JD → 再对比简历 → 再生成问题清单 → 再标出答不上的 | 单步问答的质量先稳住 |
| 主动追问 | 诊断时发现「这条经历缺量化」→ 主动问「这个项目覆盖多少商家？」→ 填回简历 | 槽位机制已有，扩展成「按需追问」 |
| 长期记忆 | 记住「哪类改写建议用户采纳了」，下次优先给同类 | 有采纳/拒绝的反馈按钮之后 |
| 工具分级 | 只读（检索/统计）自动执行；写操作（改简历文件）必须确认 | 引入写操作时 |

### 到这一步才该重新评估要不要上框架

现在不用 LangChain 的理由见 README 设计决策 ⑨。**到 v3.0 有三条会变**：

1. 多步规划 + 状态机 + 失败重规划 —— 自己写开始重复造轮子
2. 需要 step-level trace —— 这是框架生态真有优势的地方
3. 工具数量上来后需要统一的接入方式 —— **但这一条我会先看 MCP，不是 LangChain**

> 判断标准和「要不要上 Agent」是同一个：**先问确定性/手写方案够不够，不够才加那一层。**
> 差别在于框架的成本更隐蔽——它不表现为 bug，表现为**你失去了对细节的控制**
> （比如提示词拼装顺序，那一点直接影响账单）。

> ⚠️ **要不要上 Agent，先过这个判断**：路径能事先枚举清楚吗？
> 能 → 用确定性流程更稳更省。现在多数问题路径是固定的，所以**现在不该上 Agent**。
> 真正需要临场判断的只有「面试准备」这类复合任务。

## v3.1 · 可能永远不做

写在这里是为了记住**为什么不做**：

| 想法 | 不做的理由 |
|---|---|
| 云端同步 / 多设备 | 要有服务器和账号，就要承担别人的简历数据。个人工具不该背这个 |
| 自动投递 / 自动打招呼 | 平台明确禁止，且会伤害用户信誉 |
| 破解字体反爬 | 规避技术措施 |
| 简历自动生成 | AI 编经历是求职工具的红线 |
| 做成 SaaS 卖 | 需要托管 key、处理支付、合规审查——收益远小于复杂度 |

## 贡献方向（如果你想加功能）

最欢迎的三类 PR：

1. **新站点的选择器** —— 加在 `content.js` 的 `pick()` 列表里，不影响兜底逻辑
2. **能力组词典** —— `analyzer/config.example.py` 的 `GROUPS`，补新兴技术词
3. **标杆问题** —— `eval/golden_questions.md`，特别是**能让当前版本答错的问题**

> 最后一类最有价值：**一个能复现的 bad case 比一个新功能值钱。**
