> 几乎没有一个回答「这个结论准不准」——这里是唯一的差异化空间。

| # | 做什么 | 状态 | 为什么现在做 |
|---|---|---|---|
| 1 | **标杆集跑测脚本** —— `eval/` 里的问题批量跑，输出得分表 | ✅ 部分 | 现在改提示词全靠感觉，没有回归保护 |
| 2 | **引用校验** —— 检查回答里的【JD n】是否真的对应检索到的那条 | ❌ | 引用错位是最隐蔽的幻觉，用户不会发现 |

## v2.15 · 打通工作台（已完成）

> 插进 v2.1 和 v2.2 中间，不是原计划里的顺序。原因：`lib/pipeline.js` 的
> `funnel`/`needsFollowUp`/`failBreakdown` 早就写好了却**从未被任何界面调用过**，
> 而配套的 `career-web` 工作台在读同一批数据。补一个标签页和一个同步按钮
> 就能让两边真正连起来——比原计划排在前面的「多站点适配」紧迫得多，
> 因为那是「采更多」，这是「已经采到的还没用上」。

| # | 做什么 | 状态 |
|---|---|---|
| 1 | **侧栏漏斗标签页** —— `lib/funnelUI.js`，vanilla SVG，复用 `pipeline.js` 不重算 | ✅ |
| 2 | **云端同步** —— `lib/syncSupabase.js`，手写 REST 客户端 upsert 进 `career_jds` | ✅ |
| 3 | **设置页 Cloud Sync 区块** —— URL/anon key/邮箱密码登录 | ✅ |

**取舍记录**：
- 同步只 upsert，不删除。本地删了记录不会同步删云端——网络抖动导致的空列表
  被误当成「用户真的清空了」而级联删掉云端数据，是不可逆的损失。
- 登录用邮箱+密码而不是魔法链接。魔法链接的回调要跳回 `chrome-extension://`，
  MV3 里要绕重定向白名单和 tabs 监听，对个人工具不值得。密码在
  `career-web` 的「设置同步密码」里给同一个账号加一个即可，RLS 按
  `auth.uid()` 判断，跟登录方式无关。
- 不装 `@supabase/supabase-js`。扩展坚持零构建，SDK 要么得打包要么得
  从 CDN 远程加载，而 MV3 默认 CSP 禁止扩展页面执行远程脚本。

### 多站点适配（已确认要做，按难度分三层）

现在只有 BOSS 直聘适配完整。**先把 BOSS 用到稳，再一层层往外扩**——
每加一个站点都要重新处理它的 DOM 结构、反爬手段和协议边界，一次铺开必然全都半成品。

| 层 | 站点 | 难度 | 要处理什么 |
|---|---|---|---|
| **L0 已完成** | BOSS 直聘 | —— | SPA 内嵌详情面板 · jobId 做去重键 · 字体反爬（薪资交人工补） |
| **L1 next** | 猎聘 · 智联招聘 | 中 | 结构相对传统，多为独立详情页；启发式兜底大概率已经能抓到正文，主要是补选择器和确认字段位置 |
| **L2** | 前程无忧 · 拉勾 | 中 | 拉勾的岗位量已明显萎缩，性价比低；51job 结构较老但页面较杂 |
| **L3 单独对待** | LinkedIn | **不做扩展适配** | 见下 |

**为什么 LinkedIn 要单独判断：**

海外站已经有成熟方案 —— [JobSpy](https://github.com/speedyapply/JobSpy)（`pip install python-jobspy`）
一个库同时覆盖 LinkedIn / Indeed / Glassdoor / Google / ZipRecruiter，输出 DataFrame。

所以 LinkedIn 的正确做法不是给扩展再写一套选择器，而是**在 `analyzer/` 侧加一个可选的
JobSpy 导入脚本**，把结果转成同样的 `#元信息 + 正文` 块格式喂给 `analyze_jd.py`。

> 判断依据：**同一个问题已经有成熟方案时，接进来比重写划算。**
> 扩展的价值在于"抓登录墙后面、只有人眼能看到的页面"；公开可抓的站点没必要走扩展。

**加一个国内站点具体要做什么**（欢迎 PR）：

1. `extension/manifest.json` 的 `matches` 和 `host_permissions` 里加域名
2. `extension/content.js` 的 `scope()` 里加该站的详情容器选择器
3. `pick()` 的各字段选择器列表里补几条
4. `extension/popup.js` 的 `SITE_NAME` 里加站点名映射

**兜底策略保证即使 2~3 步都不做也能用**：启发式会扫出正文，整页文本永远兜底。
所以「支持一个新站点」的最低成本其实只有第 1 步。

## v3.0 · 从「问答」到「Agent」

**现在的对话是单轮工具调用（检索 → 生成），不是 Agent。**
要成为 Agent，得让「下一步做什么」由模型临场决定：

| 能力 | 举例 | 前置条件 |
|---|---|---|
| 多步规划 | 「帮我准备这家公司的面试」→ 自己决定：先查这家 JD → 再对比简历 → 再生成问题清单 → 再标出答不上的 | 单步问答的质量先稳住 |
| 主动追问 | 诊断时发现「这条经历缺量化」→ 主动问「这个项目覆盖多少商家？」→ 填回简历 | 槽位机制已有，扩展成「按需追问」 |
| 长期记忆 | 记住「哪类改写建议用户采纳了」，下次优先给同类 | 有采纳/拒绝的反馈按钮之后 |
| 工具分级 | 只读（检索/统计）自动执行；写操作（改简历文件）必须确认 | 引入写操作时 |

### 到这一步才该重新评估要不要上框架

现在不用 LangChain 的理由见 README 设计决策 ⑨。**到 v3.0 有三条会变**：

1. 多步规划 + 状态机 + 失败重规划 —— 自己写开始重复造轮子
2. 需要 step-level trace —— 这是框架生态真有优势的地方
3. 工具数量上来后需要统一的接入方式 —— **但这一条我会先看 MCP，不是 LangChain**

> 判断标准和「要不要上 Agent」是同一个：**先问确定性/手写方案够不够，不够才加那一层。**
> 差别在于框架的成本更隐蔽——它不表现为 bug，表现为**你失去了对细节的控制**
> （比如提示词拼装顺序，那一点直接影响账单）。

> ⚠️ **要不要上 Agent，先过这个判断**：路径能事先枚举清楚吗？
> 能 → 用确定性流程更稳更省。现在多数问题路径是固定的，所以**现在不该上 Agent**。
> 真正需要临场判断的只有「面试准备」这类复合任务。

## v3.1 · 可能永远不做

写在这里是为了记住**为什么不做**：

| 想法 | 不做的理由 |
|---|---|
| 自动投递 / 自动打招呼 | 平台明确禁止，且会伤害用户信誉 |
| 简历自动生成 | AI 编经历是求职工具的红线（`GUARD` 意图把这条写成了代码，不是靠提示词自觉） |
| 做成 SaaS 卖 | 需要托管 key、处理支付、合规审查——收益远小于复杂度 |

### ⚠️ 这张表里原来有两条，后来都做了（2026-09-10 修订）

留档比删掉重要 —— 一份**说着"永远不做"而代码已经做了**的路线图，
比没有路线图更误导：读文档的人（包括三个月后的我自己）会据此判断项目边界。

**① 「云端同步 / 多设备」**

原来的理由是「要有服务器和账号，就要承担别人的简历数据」。

这个判断本身没错，但它假设了一种实现方式：**我提供服务器**。
实际做法（v2.15）是**用户自带 Supabase 项目** —— URL 和 anon key 由用户自己填，
数据在用户自己的库里，RLS 按 `auth.uid()` 隔离，我这边**没有任何服务器、
拿不到任何人的数据**。责任边界完全不同，所以原来的理由不适用。

代价照实说：这条路要求用户自己开一个 Supabase 项目、跑一遍 `schema.sql`、
再在两端各填一次配置。**门槛真实存在**，只是它换来的是"我不碰你的数据"。

**② 「破解字体反爬」**

原来的理由是「规避技术措施」，而 `extension/lib/glyphmap.js` 已经实现了
私有区码位 → 数字的还原。**这是用户明确要求的**（原话：「解 PUA 码位到数字的
映射，无论如何，处理一下」），我提出过顾虑，用户重申，于是做了。

事后看，原来那行字把两件不同的事混在了一起：

- 「破解字体」= 拿到字体文件、逆出映射表、硬编码进代码分发 —— 这个仍然不做
- 实际做的 = 在**用户自己有权浏览的页面上**，把网站自己加载的那个字体
  渲染到 canvas，和 0–9 的字形比对像素。不下载字体、不分发映射表、
  不绕过任何访问控制，读的就是**屏幕上已经显示给用户看的东西**

这个区分是真实的，但我不打算把它写成"所以原来那条本来就不适用" ——
更准确的说法是：**判断改了，而改的依据是用户的决定 + 一个更细的区分。**
PRD §1.3 那条同步修订。

> 这两条合起来是这份路线图最该被记住的一点：
> **"永远不做"这种表述几乎总会过期。** 有价值的不是那个结论，
> 是结论背后的**判断依据** —— 依据变了，结论就该跟着改，
> 而且要说清依据的哪一部分变了。

## 贡献方向（如果你想加功能）

最欢迎的三类 PR：

1. **新站点的选择器** —— 加在 `content.js` 的 `pick()` 列表里，不影响兜底逻辑
2. **能力组词典** —— 现在的权威源是 `career-web/src/data/skills.json`
   （`analyzer/config.example.py` 的 `GROUPS` 是**另一套已经分叉的旧词典**，
   合并排在 P2.7）。改完跑 `npm run check:shared -- --fix`
3. **标杆问题** —— `eval/golden_questions.md`，特别是**能让当前版本答错的问题**

> 最后一类最有价值：**一个能复现的 bad case 比一个新功能值钱。**
